# QA Pass — Findings, Fixes, and Handoff

Tested against the local docker-compose stack (nginx/backend/frontend/postgres) with sanitized
synthetic data (~185 candidates, 210 resumes, 1533 evaluations, 13 job roles, 7 users across
every role) generated by `backend/scripts/gen_synthetic_data.py`. No real candidate data or
production systems were touched. Testing combined direct API calls (matching the real request
shapes the UI sends) and a real headless-browser driver (Playwright) that logs in through the
actual `/login` form and drives the actual rendered pages — see
`qa/bugs/findings.json` and `qa/bugs/screens/*.png` for raw run output and screenshots.

## Confirmed bugs

### 1. `GET /audit-log` has no admin/role check — any authenticated user can read the full audit trail
**Status: fixed.**

- File: `backend/app/routers/audit.py` — the endpoint depended on `get_current_user` (any active
  user, any role), not `require_admin`.
- Repro (pre-fix): log in as a non-admin (`interviewer1@tektalis-test.com` / `QaTest!2026`), then
  `GET /api/audit-log` with that user's bearer token → 200 with the full audit log, including
  other users' logins, candidate deletes/restores, stage changes, etc.
- Impact: `AuditLogs.tsx` also had no client-side gate (only the NavBar link is hidden for
  non-admins), so a recruiter/interviewer/hiring_manager who simply typed `/audit` in the
  address bar saw the same admin-only audit trail a real admin would.
- Fix: swapped the `get_current_user` dependency for `require_admin` in `audit.py`, matching
  how `admin.py` and `shortlist.py`'s `erase` endpoint gate admin-only actions. Added a matching
  client-side gate to `AuditLogs.tsx` (mirrors the "Ask an admin…" pattern already used in
  `EmailIngestion.tsx`) so non-admins get a clear message instead of a page that silently 403s.
- Regression tests added: `tests/test_api.py::test_audit_log_rejects_non_admin` (recruiter → 403),
  `tests/test_api.py::test_audit_log_allows_admin` (admin → 200). Both pass.
- Verified post-fix via Playwright: interviewer hitting `/audit` now sees "Audit logs are only
  visible to admins"; admin still sees the full table (50 rows in the seeded dataset) — no
  regression for the legitimate case.

### 2. `/gdpr` (Data Retention panel) has no client-side role gate or error state
**Status: fixed.**

- File: `frontend/src/pages/DataRetentionPanel.tsx` — unlike `Users.tsx`/`EmailIngestion.tsx`,
  this page had no `role === 'admin'` check and no error UI for a failed settings fetch.
- Backend was already correctly gated (`GET/PUT /admin/gdpr/settings` → 403 for non-admins,
  confirmed via direct API call), so no GDPR configuration data ever actually leaked. The bug
  was purely front-end: a non-admin visiting `/gdpr` saw the full interactive retention-policy
  form (toggle, days input, Save button) with no indication that submitting it would silently
  fail.
- Fix: added the same `role === 'admin'` gate as `AuditLogs.tsx`, disabled the settings query
  for non-admins (`enabled: isAdmin`), and show an "only visible to admins" message instead of
  the form.
- Verified post-fix via Playwright: interviewer hitting `/gdpr` now sees the gated message;
  admin still sees the full retention form — no regression.

### 3. Backend: `_JdSkillItem` undefined name — `POST /skills/extract-full-config-from-file` crashes when it actually finds a skill
**Status: fixed.**

- File: `backend/app/routers/skills.py` — the handler referenced `_JdSkillItem(...)` to build
  the `skills` list, but that class was never defined anywhere in the module. It also passed
  `skills=`/`metadata=` kwargs into `_JdFullConfigResponse`, which didn't declare those fields —
  so even on the rare path that *didn't* crash (empty skills list), the extracted title/degree/
  experience data was silently discarded and the endpoint always returned an all-null response.
- Repro (pre-fix): confirmed directly — `_JdFullConfigResponse(skills=[_JdSkillItem(...)], ...)`
  raised `NameError: name '_JdSkillItem' is not defined` whenever the skill dict was non-empty;
  with an empty dict it returned 200 but every field was null regardless of the uploaded file's
  actual content.
- Current user impact: **none today** — `frontend/src/api/client.ts`'s `extractFullConfigFromFile`
  wrapper exists but is never called from any page (verified via repo-wide search); the real
  "Upload File" JD-autofill flow on `AddJobPage.tsx` uses `extractJdText` + `extractFullConfigFromJd`
  + `extractSkillsFromJd` instead. This is a latent defect in an unused-but-public endpoint, not
  a live regression.
- Fix: added the missing `_JdSkillItem` model and the `skills`/`metadata` fields to
  `_JdFullConfigResponse` (`backend/app/routers/skills.py`). Verified post-fix: the endpoint no
  longer crashes and correctly returns extracted skills/metadata (tested with both an
  empty-skills document and one that matches the skill dictionary).
- Regression tests added: `tests/test_api.py::test_jd_full_config_response_accepts_skills_and_metadata`,
  `tests/test_api.py::test_extract_full_config_from_file_returns_matched_skills`. Both pass.

### 4. Leaderboard: Blind Mode, Auto-Shortlist, and Reclassify-Experience-Levels were fully built but unreachable from the UI
**Status: fixed.**

- File: `frontend/src/pages/Leaderboard.tsx:722-725` (pre-fix) —
  ```
  // Satisfy noUnusedLocals for temporarily disabled UI controls/mutations
  if (false as boolean) {
    console.log(toggleBlindMode, _autoShortlistMut, _reclassifyMut)
  }
  ```
  All three features had complete, working state/mutation logic (`blindMode` masking was even
  already wired into `CandidateTable`/`NeedsReviewBuckets` as a prop) but no button anywhere
  called `toggleBlindMode()`, `autoShortlistMut.mutate()`, or `reclassifyMut.mutate()`. A real
  user testing "as a real user" simply could not find Blind Mode anywhere on the page —
  confirmed by browsing the rendered Leaderboard and finding no such control.
- Impact: Blind Mode is a marketed bias-mitigation feature (README's "Blind Evaluation" /
  `pii_scrubber.py`); Auto-Shortlist and bulk experience-level reclassification are documented
  recruiter workflows. All three were 100% dead on arrival for any user of the deployed app.
- Fix: removed the dead-code guard; wired `Blind Mode` / `Auto-Shortlist` / `Reclassify Levels`
  buttons into the Leaderboard toolbar (`frontend/src/components/Leaderboard/FilterControls.tsx`),
  matching the existing Pause/Resume/Email-Shortlisted button style and admin-gating pattern.
- Verified post-fix via Playwright: Blind Mode toggle now masks names as "Candidate #N" in the
  table; Reclassify Levels button renders; Auto-Shortlist button renders once a job role is
  selected (it's intentionally gated on `isAdmin && selectedJobRoleId`, same as the pre-existing
  Email-Shortlisted button).

### 5. `PATCH /candidates/{id}` crashes with a bare 500 on an invalid `stage` value
**Status: fixed.**

- File: `backend/app/routers/candidates.py` — `CandidateUpdate.stage` had no validation
  (`Optional[str] = None`), unlike the sibling `PATCH /results/candidates/{id}/stage` endpoint
  (`results.py`), which validates the same enum via a Pydantic `pattern`. This was flagged as a
  risk in `qa/INVENTORY.md` (E6.6 — "the two stage-update paths don't produce inconsistent
  states") and confirmed by direct reproduction.
- Repro: `PATCH /api/candidates/151` with `{"stage": "totally_bogus_stage_xyz"}` → bare
  `Internal Server Error`, 500. Backend logs show an unhandled `sqlalchemy.exc.IntegrityError`
  (`psycopg2.errors.CheckViolation`) from the DB's own `candidates_stage_check` constraint —
  the constraint correctly protects data integrity (no bad value is ever persisted, confirmed
  the candidate's `stage` was unchanged afterward), but the application layer never validates
  before hitting it, so a routine bad-input request surfaces as an unhandled crash instead of a
  clean 422.
- Fix: added the same regex pattern (`^(applied|screening|coding|interview|offer|hired|rejected)$`)
  already used by `results.py`'s `UpdateCandidateStageRequest` to `CandidateUpdate.stage`.
- Verified post-fix: the same request now returns 422 with a clear Pydantic validation message;
  a valid stage value still updates correctly (200).
- Regression tests added: `tests/test_api.py::test_patch_candidate_rejects_invalid_stage`,
  `tests/test_api.py::test_patch_candidate_accepts_valid_stage`. Both pass.

### 6. `POST /candidate/apply/{role_id}` crashed on every call that included a resume file
**Status: fixed. Severity: high — this broke the entire candidate self-application flow.**

- File: `backend/app/routers/candidate_portal.py` — `candidate_apply()` had two local imports
  of functions that don't exist anywhere in the codebase:
  `from app.services.deduplicator import compute_simhash` (real name: `compute_fingerprint`,
  already used correctly by `upload.py`) and `from app.services.segmenter import segment_resume`
  (real name: `detect_sections`).
  Nothing else in the test suite or codebase exercises `candidate_portal.py`, which is exactly
  why this went unnoticed — this is precisely the kind of defect "test as a real user" is meant
  to catch that unit tests around individual services miss.
- Repro (pre-fix): as the seeded candidate-portal QA account, `POST /candidate/apply/{role_id}`
  with a resume file attached → bare `Internal Server Error`, 500. Logs show
  `ImportError: cannot import name 'compute_simhash' from 'app.services.deduplicator'` — the
  request never got past the import statement, so this failed 100% of the time, for every
  candidate, on the very first line of the resume-processing branch.
- Fix: corrected both imports and their call sites to the real function names.
- Verified post-fix end-to-end: applied with a real resume file → 202, application appears in
  `GET /candidate/applications` once the background evaluation finishes (score computed
  correctly), matching the documented flow.
- Follow-up check: wrote a small AST-based static sweep (see `qa/bugs/` session notes) that
  parses every `.py` file in the backend and verifies every `from app.X import Y` — including
  the lazy, function-local imports like these two — actually resolves to a real name in the
  target module. Ran it across the whole backend: **zero other instances** of this bug pattern
  exist elsewhere in the codebase.
- Regression test added: `tests/test_api.py::test_candidate_portal_dependencies_are_importable`
  (imports the real functions to catch a future rename, and statically asserts the exact typo'd
  names never reappear in `candidate_portal.py`'s import list). Passes.

### 7. 180-day re-apply freeze had a race window — rapid duplicate `/apply` calls bypassed it
**Status: fixed. Found while manually verifying the fix for #6.**

- File: `backend/app/routers/candidate_portal.py` — the freeze check queries for an existing
  `Evaluation` row (`Evaluation.evaluated_at >= cutoff`) to decide whether the candidate already
  applied recently. But that `Evaluation` row was only ever created by a **background thread**
  spawned *after* the HTTP response was already sent — so a second `/apply` call arriving before
  that background thread got around to running found no matching row and sailed through the
  freeze check.
- Repro (pre-fix): applied to a job role, then immediately (same second) applied to the same
  role again → both calls returned `202 submitted`, no freeze error, even though the documented
  behavior is a 400 on the second call. (This is exactly edge case E13.2 flagged in
  `qa/INVENTORY.md` before any testing began.)
- Fix: `candidate_apply()` now calls the existing `_queue_evaluation()` helper from
  `evaluate.py` (already used by the admin-triggered `/evaluate` flow to synchronously mark a
  resume as `eval_status="queued"` before background scoring starts) *synchronously*, before
  spawning the background thread. This closes the race by the same means the rest of the app
  already uses for the analogous ordering problem — no new mechanism introduced, just reusing
  the app's own established synchronous-queue-then-background-score pattern.
- Verified post-fix end-to-end: apply → immediately re-apply to the same role → second call now
  returns 400 with the correct "already applied... apply again on {date}" message; the first
  application still completes and scores correctly afterward (confirmed the pre-inserted queued
  row gets updated in place by the background scoring pass, not duplicated — no unique-constraint
  violation).
- Not covered by an automated regression test: reliably reproducing a race condition in a unit
  test would require either sleeping past real thread timing or deeply mocking the threading
  module, both fragile. Verified instead by direct reproduction against the running app
  before and after the fix (documented above) — flagging this so a future contributor knows the
  fix is manually verified, not test-locked.

### 8. `POST /auth/login` never checked `is_active` — a revoked account could still log in
**Status: fixed.**

- File: `backend/app/routers/auth.py` — `login()` checked the password but never checked
  `user.is_active`. `get_current_user` (`app/deps.py`) *does* check it on every subsequent
  request, so the practical exposure was bounded — a revoked user got a real-looking token pair
  back from `/login` (misleading "success") that then 403'd on their very first actual API call
  — but login itself gave no indication anything was wrong.
- Repro (pre-fix): admin revokes `recruiter2` (`PATCH /admin/users/{id}/revoke`, confirmed
  `is_active:false` in the response) → `POST /auth/login` for that same account still returned
  200 with valid `access_token`/`refresh_token`.
- Fix: `login()` now checks `is_active` right after password verification and returns 403
  ("Account has been revoked. Contact your administrator.") — same message and status
  `get_current_user` already uses, so the behavior is consistent end-to-end.
- Verified post-fix: revoke → login → 403; restore → login → 200 again.
- Regression test added: `tests/test_api.py::test_login_rejects_revoked_user`. Passes.

## Investigated, not bugs

- **Leaderboard showing several candidates tied at score 100 at the top of the default sort** —
  looked like a scoring-engine bug at first glance. Checked the DB: only 7 of 1533 evaluations
  are exactly 100; they cluster visually only because the table defaults to sort-by-score-desc.
  Not a defect.
- **`POST /skills/extract-full-config-from-jd` (text-paste path) returning no `skills` field** —
  by design; that endpoint's docstring and the frontend (`AddJobPage.tsx::handleExtract`) both
  treat it as metadata-only and call the separate `extractSkillsFromJd` endpoint in parallel for
  skills. Not a defect.
- **Early test run showing several "failed" logins for synthetic recruiter/interviewer accounts** —
  self-inflicted: the synthetic users were created with `@tektalis-test.local` email addresses,
  and `.local` is an RFC 2606 reserved TLD that pydantic's `EmailStr` rejects at `/auth/login`.
  Fixed by renaming to `@tektalis-test.com` (both in the seeded DB and in
  `backend/scripts/gen_synthetic_data.py` for future reruns). Not an app bug.
- **`auth-invalid-login-shows-error` (and, on one run, `candidate-dashboard-loads`) flaked in
  the automated harness** — two *separate* rate limiters stack on `/auth/login`: nginx's zone
  (burst 5, leaks 1/6s) and the backend's own DB-backed limiter
  (`app/middleware/rate_limit.py`), which is a strict sliding window capping any IP at 5 requests
  per trailing 60s — not a leaky bucket. The harness makes 6 logins per run (1 invalid-login
  check + 5 role logins); anything spaced closer than ~13s apart packs all 6 inside one 60s
  window and the 6th one 429s, regardless of which check that happens to land on. Verified the
  real app behavior in isolation first (a single fresh browser, no prior requests, correctly
  shows "Incorrect email or password"), then fixed the harness itself
  (`qa/playwright/run.js` — this session's driver script) to space every login ≥13s apart.
  Not an app bug — was a test-harness pacing bug, now fixed so the suite is deterministic.

## Pre-existing test suite health
**Status: fixed.**

The full `tests/` suite had **11 pre-existing failures unrelated to anything touched in this
session** — confirmed by re-running the exact same suite against a git-stashed (pre-session)
copy of the code, which failed identically. Each was a test that had gone stale after an
intentional refactor elsewhere in the codebase, not a real defect:

- `test_login_success` — mocked `app.routers.auth.authenticate_user`, which no longer exists;
  current `/auth/login` queries the DB directly and calls `verify_password`. Rewrote to mock
  `verify_password` + `get_db` and assert against the real `Token` response shape
  (`access_token`/`refresh_token`/`role`/`email`).
- `test_get_results`, `test_bulk_rerun` — the original file called
  `app.dependency_overrides.clear()` at **module scope**, right after the function definitions.
  Since that's not inside a fixture, it executed immediately at import time — clearing the
  overrides before pytest ever invoked the test functions, so every request hit real auth and
  got 401. Fixed by moving the override set/clear into each test function body (`try`/`finally`),
  matching the pattern already used for the new audit-log tests. Also updated the mocked query
  chain to survive the `.join(...)` calls `results.py` now makes (soft-delete filtering added
  since this test was written), and corrected `test_bulk_rerun`'s expected status from 200 to
  202 (`/evaluate/bulk-rerun` is a background-task endpoint, per its own docstring).
- `test_get_results` itself was rewritten from asserting a nested `candidate: {name: ...}` shape
  (which doesn't exist in the current flat `ResultsResponse` schema) to asserting the empty-page
  contract instead (`items: []`, `total: 0`, `pages: 1`) — deep-mocking every field of the
  current response builder (job_role/resume/candidate relations, JSON-parsed skill lists) would
  be fragile and low-value; the empty-page contract is stable and still catches real breakage.
- 4 tests in `test_parser.py::TestPDFParsing` — the mocked PyMuPDF `page` object never set
  `page.rect.width`, which the parser's newer two-column layout detection
  (`_blocks_in_reading_order` / `_find_column_split`) now reads. Added a real width value to the
  mock. One of those tests also needed its sample block text padded past parser.py's 100-char
  "needs OCR" floor (also added since these tests were written).
- `test_deduplicator.py::test_minor_changes` — asserted two short sentences with several
  word-level differences would be "near-duplicate" (Hamming distance ≤5); actual distance is 16.
  SimHash operates on character 3-grams, so that expectation was never going to hold for that
  input — not a regression, just untested-against-reality test data. Replaced with a
  single-word tweak in a longer, realistic paragraph (distance 5), which matches the real-world
  near-duplicate scenario the app's own dedup logic is meant to catch.
- Both tests in `test_scorer.py` — mocked `scorer.get_confidence` and a semantic
  embedder/cosine-similarity model; the scorer has since been rewritten to a keyword+TF-IDF
  matcher with an LLM-first path (`get_confidence` and the embedder call are gone from this
  code path entirely). Rewrote as a black-box behavioral test: mock `score_with_llm` to return
  `None` (forces the deterministic keyword fallback, avoids a real network call to the LLM
  provider) and assert on realistic input that a skill present in the resume text is matched
  and one that's entirely absent is a gap — robust to future internal scoring changes.
- `test_segmenter.py::test_standard_headers` — expected 3 sections; segmenter now correctly
  keeps text appearing before the first recognized header as a 4th "summary" section (per the
  most recent commit's own intentional fix, "prevent segmenter.py from discarding resume text
  that appears before the first recognized standard header"). Updated the expected count and
  section ordering.
